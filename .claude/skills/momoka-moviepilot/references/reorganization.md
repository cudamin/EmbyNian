# 历史记录、预览与重新整理

## 找的是哪一份文件

Emby 的 `Path` 常是 MoviePilot 已整理后的目标，甚至是软链接。不要直接把它当新下载源提交。

1. 通过 `history/transfer` 的片名/文件名查询分页收齐候选，读取 `id/src/dest/src_fileitem/dest_fileitem/mode/status`。
2. 精确匹配 Emby 当前路径，原目标匹配优先于后续记录的源路径匹配。多个候选需要明确选择；零候选不能退而整理父目录。
3. 提交原记录的 `logid` 或支持的 `logids`。已成功移动的记录从原目标重新整理，其余通常从原源重新整理；以该版本服务端实现为准。
4. 预览前确认服务端可见的具体 FileItem。只按文件清单处理；目录、缺文件或批量截断不应悄悄扩大/缩小用户范围。

`from_history` 表示**复用旧识别结果**，不是“从原记录找文件”。打开它可能把用户手填的新媒体编号、季号、集号覆盖回旧值。修改季集应保留 `logid`，关闭 `from_history`。

## 目录配置是整体

`transfer/manual/target-path` 不只返回路径，还可能返回：

- `target_storage`、`target_path`、`transfer_type`；
- `scrape`；
- `library_type_folder`、`library_category_folder`。

路径正确但漏掉类型分类，仍可能把电视剧放到 Emby 库扫描范围外。默认值来自匹配结果，不能一律写 false。更换目录后，应重新核对这组配置。

## 不可跳过的提交边界

- `preview:true` 只出预览；预览成功不等于实际已整理。请求体与对应版本必须能证明这是只读操作。
- 所有选择文件都必须出现在预览中，源和目标明确，无失败才允许确认。仅 `success:true` 或“有一行绿色”不足以提交一批文件。
- 修改表单任意字段、新选择记录、连接/账号变化均使旧预览失效；异步回话核对发起时的版本，避免新表单套上旧预览。
- `reorganize` 可能清理匹配的成功历史和旧目标；`skip_success` 与它的优先级要查版本。即使 `reorganize:false`，按 logid 重整也可能清理原目标，不能把关掉开关当作无副作用。
- 检查其他软链接是否以旧目标为源：按旧目标路径查询完整历史，不能只按原片名查；同一批次内存在这种依赖也先停。提交前重核原历史快照，包括 FileItem 的存储、类型、路径及复用的媒体身份，路径字符串相同不代表仍是同一个文件。客户端重核无法代替服务端原子提交，检查与执行之间仍有竞态。
- 清理一个链接可能让未点名的另一个链接失效；不自动级联重整、删除或修复。
- 确认必须列明实际源、目标、方式、清理/覆盖影响。同一个 WinUI XamlRoot 不能同时显示两张 ContentDialog；用同窗确认或正确结束前一弹窗，不能把弹框异常吞成“用户取消”。
- 提交中锁住再次提交，拿不到明确回执不自动再发一次。只有鉴权在副作用前明确拒绝时，才可按客户端契约重登一次；超时不证明服务器没做。
- 预览使用文件集合和回执快照并只消费一次；实际发出过的历史/文件在本进程内不能靠重新预览绕过防重。accepted、部分成功和不明回执后保留逐项结果，先去 MoviePilot 核对。当前没有自动核对后解锁的流程，不能把重启客户端当成安全重试证明。

## 如何判断成功

- `accepted`：已接收，尚未完成。
- `completed`：对应文件完成。
- `failed/retry_wait/manual_review/skipped` 各自如实显示；部分成功保留逐文件回执，不能把整批重新发出。
- 若老版本只返回空成功信封，报告“服务器已接收，完成状态待确认”，不能伪造 completed。
- 核对整理历史新记录及目标文件；源文件保留与否要符合所选整理方式。需要刷新 Emby 时按已授权范围操作，不把单集整理扩大成全库重扫。
- Emby 可能在刷新后重新命名条目，旧 ID 也可能失效；以季集、路径和媒体身份验证，不只对标题。没有播放就不能报告播放通过。

## 夹具优先覆盖

软链接再次作为源的历史链；移动与复制/链接的源选择；多候选；分页未收齐；主身份跨来源冲突；任一文件预览缺失；修改字段后旧回话；换服务器但相同 logid；依赖旧目标的其他记录；部分成功与请求结果不明。
