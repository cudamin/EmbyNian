# EmbyNian — WinUI 3 shell terrain

EmbyNian is a WinUI 3 + Windows App SDK + .NET desktop client, unpackaged and x64. Read SDK and package versions from the project files, not this skill. Use the current working tree; an absolute path from another session is not its root.

**Policy lives in [CLAUDE.md](../../../CLAUDE.md).** This file explains the implementation and its constraints; general WinUI practice comes from the `winui-*` skills where it does not conflict with project policy. `PROGRESS.md` is the current-work and historical-evidence record. Before adding a service, inspect `src/EmbyNian.Shell/Composition/ShellServices.cs`, the registration site.

Playback is the `embynian-playback` skill; the gate procedure is `embynian-verification`; shaders and 画质档位 are `mpv-shader-quality`.

## Three projects

- **`src/EmbyNian.Core`** — no UI references; currently no packages or project references. Package-free is a lightweight default, not a prerequisite for unit testing.
- **`src/EmbyNian.Shell`** — the WinUI shell. WindowsAppSDK is split into sub-packages rather than the meta-package to control payload size. The project file is authoritative for package selection and versions; review new runtime payloads during upgrades. `WindowsPackageType=None`, x64, `DISABLE_XAML_GENERATED_MAIN` with a hand-written `Program.cs`.
- **`tests/EmbyNian.Tests`** — currently package-free and referencing Core, with `OutputType=Exe` and a hand-written harness. `dotnet run` is the runner. Register new suites in `Program.cs`; compilation and run order are in CLAUDE.md.

## The shell's terrain

UI views are in `src/EmbyNian.Shell/Views/`, view models in `ViewModels/`, and registrations in `Composition/ShellServices.cs`. Entry points include the shell, home/library/detail/settings pages, server dashboard and player, with reusable controls such as `PosterCard`, `HomeBanner` and `EpisodeRow`. Enumerate the current files when a change spans the UI; an illustrative list here is not a completeness check.

`PlayerPage` is a sibling `UserControl` of the navigation shell rather than a page inside its `Frame`. It hosts the integrated composition pipeline; standalone playback uses mpv's own top-level window and uosc. See `embynian-playback`.

## Where capability lives

**`ShellServices.Build(AppPaths)` is the registration site.** It enables `ValidateOnBuild` and `ValidateScopes` and must run on the UI thread because `IUiDispatcher` captures that thread. Check the existing registration lifetimes before adding a dependency; the current use of singletons is not a reason to give every future object application lifetime.

Most non-UI capability sits in `Core/Emby`, `Core/Playback`, `Core/Mpv` and `Core/Configuration`; `Core/Services` contains selected services rather than all capability. Use dependencies and lifetime to decide whether a type needs registration. Moving a file into a folder named Services changes neither.

**Use the layering policy in CLAUDE.md.** Important business decisions, reusable calculations and regression-prone algorithms belong in testable Core code; local presentation predicates may remain near the UI. The current test-project reference is not a reason to extract every conditional. Existing reusable rules include:

`HomeLayout` (which home rows, in what order, and only writing settings back when something really changed), `ScreenPlacement` (which monitor, restoring geometry), `ItemArtwork.SamePictures`, `CardSize`, `ImageCachePolicy` and `LruCache` (eviction), `LoadGeneration` (which load is still the current one), `ItemMenu.For` (which menu rows and their wording), `CardStrip`, `WrapLayout`, `HomeCarousel`, `ItemMetadataEdit`, `EpisodeNavigation`, `TrackSelection` / `TrackLanguagePriority`, `StartupArgs`.

## Pages, view models, `Attach`

A WinUI page must have a parameterless constructor and is built by the framework rather than the container, so constructor injection into pages is a dead end. **Pages construct their own view models; dependencies arrive afterwards through `Attach(...)`.** The price is nullable service fields plus a ring of "not attached yet, return early" guards — that isn't a shortcut, write it that way. Two guard shapes are both in use: a `private bool Attached => _settings is not null;` followed by `if (!Attached || … ) return;` (DetailViewModel), or a direct field check `if (_images is not { } images) return;` (HomeViewModel, LibraryViewModel, ServersViewModel, SettingsViewModel).

**`PlayerViewModel` is the only view model in the container**: a film keeps playing behind the library page, so its state has to outlive any navigation. `ShellPage.AttachWindow` resolves it and hands it to the page. `HomePage` marks its single resolution site with a comment saying it is the one place the page resolves anything — keep that habit, because a page reaching into the container from five places is how this rule rots.

Known deviation, not a template: `FilterPanelViewModel` is `new`ed with no `Attach` at all.

## Interfaces

**Don't invent an interface just because a class goes into DI** — with no second implementation and nothing to substitute or isolate, register the concrete class, which is what most registrations here do.

`ISecretProtector` separates platform protection from Core. `ISettingsService`, `IServerCapabilities`, `IUiDispatcher`, `IClipboard`, `ISystemLauncher` and `IShellActions` narrow access to capabilities: a page that needs settings should not acquire unrelated session or player operations. Keep that boundary even when only one production implementation exists; inspect current registrations and tests instead of maintaining counts here.

For a single operation, a method delegate may express the boundary more clearly than a new interface. Settings receives `PlaybackService.ApplySubtitleStyleAsync` without receiving play/stop/seek capabilities; the backend factory is also passed as a delegate. Use an interface when several related operations or a substitutable contract warrant it.

## Code-behind

The rule — pure UI behaviour may stay there, business capability may not — is in `CLAUDE.md`. **The test is "did business logic leak in", not "is there a binding".** Live examples: `ShellPage.xaml.cs` (the `_trail` / `_forward` breadcrumb stacks, library items built from what the server returned), `PlayerPage.Input.cs` (the three window buttons, which exist only on the player's title bar), `PosterCard.xaml.cs` (the hover layer). The counter-example: page-level busy/notice is *not* a code-behind toggle — it is a derived property on `PageViewModel` with `[NotifyPropertyChangedFor]`.

The one known exception, `Views/ItemCommands.cs`, is a static class, so it structurally cannot be in the container; it takes an `EmbySession` as a parameter through every method and drives the card context menu's commands. It does **not** hand-roll HTTP: every round trip goes through `session.ExecuteAsync` and then `EmbyClient`, funnelled through `AskAsync` / `TellAsync` / `RunAsync`. The field rules for metadata editing already moved out into `Core/Emby/ItemMetadataEdit.cs` and are pinned by tests there. **Old debt, not a template — don't copy the shape**, and don't refactor it into a service unless the user asked for that.

## Colours: the role table, and why literal hex hides

Themes are declared in `src/EmbyNian.Core/Theming/UiThemes.cs`. Base colors expand into role colors through `UiTheme` / `ThemeColor`; `ThemeHost.cs` publishes the runtime brushes, while `Theme/Palette.xaml` supplies the first frame and `Theme/Styles.xaml` holds shared styles.

**Use role colors and the review procedure in CLAUDE.md.** The shipped themes are currently all dark, so screenshots alone may miss a hard-coded color. `AgreementsTests` checks literal-color growth, while palette self-checks check role completeness; neither proves the rendered result is correct. Keep the deliberately retained light half of `UiTheme` unless its documented rationale changes.

**The three dictionaries in `Palette.xaml` are keyed `Dark`, `Light` and `HighContrast` — there is no `Default`** (renamed 2026-09-05 for `winui-design`'s rule). Two consequences when adding a key: it has to go into **both** `Dark` and `Light` or the self-check's 「调色板浅色主题完整性」 fails, and there is no longer a fallback dictionary to catch a typo — a misspelled theme name now resolves to the framework's own value instead of quietly borrowing ours. Five places name these keys (`ThemeHost.Painted`, `ShellSelfCheck.Theme`'s `PaintedDictionaries` and its `PaletteKeys` call, `ShellSelfCheck.Run`'s `PaletteKeys` call, and `App.xaml`'s pinned `RequestedTheme`); the two `PaletteKeys` call sites are the ones a rename is most likely to miss, because only gate 4 notices.

## XAML traps already paid for

The platform-wide ones — `x:Bind` defaulting to `OneTime`, `TextBox` needing `UpdateSourceTrigger=PropertyChanged`, `Converter={x:Null}` blowing up at runtime, attached properties needing static setters from C# — belong to `winui-design` and `winui-code-review` now and are deliberately not copied here, and since 2026-09-05 `Microsoft.WindowsAppSDK.Analyzers` reports them in gate 1 (wired in by `Directory.Build.props`; **`WUI2010` is the one rule this project turns off, reasoning in the Shell csproj**). The ones below are this codebase's own.

- **A `RenderTransform` that mirrors an element needs `RenderTransformOrigin` written out.** `ScaleX="-1"` flips about the element's *top-left* by default, not its centre, so the picture slides a full element-width sideways — and when the element already sits against that edge, it lands entirely off the band. `HomeBanner`'s ambience wings carried that bug for a day (added 2026-09-10, fixed 09-11): size, position, mirror transform, alignment and source were all correct and `Probe` asserted every one of them, while the screen showed flat base colour the whole time. **The one pixel reading taken there missed it as well**, because that base colour is the same `#0C0E11` the scrim brushes are made of, so the scrim's own ramp read as "the wing has content". What caught it was dumping a scanline and seeing 14.3 dead flat across 300 px. A property-level assertion cannot see this; the probe now asserts the origin too.

- **An `Image` does not fill its cell — when a picture has to cover a box, it goes in an `ImageBrush`.** Under `Stretch="Uniform"`/`UniformToFill` WinUI's `Image` sizes itself to the *content* (09-10's banner batch measured "the element is the picture"), and its `ActualWidth`/`ActualHeight` then report the drawn picture rather than the layout box — so a reading taken off them can call a picture that overflows the band "filling it". `HomeBanner` hit both halves on 2026-09-11 while making the photo cover the band edge to edge: with `Stretch="UniformToFill"` the elements measured 1014×570 inside a 1014×341 band, and the screen showed the picture anchored at the band's **top** — the bottom 40% (the flower field) cut off, i.e. not the centred crop `UniformToFill` promises. Writing `Width`/`Height` = the band's inner box changed nothing. Caught by the self-check's own `PictureRead`, not by `Probe` (which had asserted the stretch mode, the alignment and the source and was green). Fix: two **empty** `Grid`s whose `Background` is an `ImageBrush Stretch="UniformToFill"` (its `AlignmentX`/`AlignmentY` default to `Center`, and a `Panel` with a background really does stretch to its cell) — the copy lives in the brush (`((ImageBrush)layer.Background).ImageSource`), and the element's size is then a box worth asserting on.

- **Keep an `ItemsSource` collection instance stable, and choose the update operation for the change.** `ObservableCollection` notifies on item additions, removals and moves; item-property changes need their own notifications. Incremental updates avoid disturbing selection or rebuilding every card. Use `Clear()` plus refill for a genuine whole-list refresh, not every small change. Replacing the collection without the required property notification can leave the binding on the old instance.

- **A visibility predicate that gains a conjunct on `IsCompact`/`HeroCard` must join `PageWidth`'s notify list — that is one half of its life; `AnnounceShape` is the other.** The 09-12 column/tail split gave `PickersVisibility` a `!HeroCard` half and the list only got `ColumnPickersVisibility`: on the episode page opened wide, the tail pickers evaluated Collapsed and nobody re-asked after the window crossed 1024 — 媒体源/音频/字幕 gone in the narrow window, not one error anywhere (fixed same day; the same batch's `VideoLineVisibility` and `HeroContentAlignment` carried it too). The attribute list on `DetailViewModel.PageWidth` is the tripwire: every property whose getter reads `IsCompact`, `HeroCard` or `IsEpisodePage` needs an entry there *and* a raise in `AnnounceShape`, because each of the two inputs can flip while the other's notification says nothing.

- **Inside a `StackPanel`, a direct child is full-bleed — it does not inherit the inset its siblings get from a sibling `Viewbox`/inner panel.** `DetailPage.HeroTail` stacks two things: a `Viewbox` whose child carries the whole tail's padding (`TailInset`), and the episode band, which is the `StackPanel`'s own child so it spans the panel edge to edge. That is by design while the band stands on the dark scrim (it is deliberately the wide one); it stopped being design on 2026-09-12, when the whole tail gained a card behind it — the band then painted its opaque fill **over** the card from x=0, taking the card's left and right margins and all four corners with it, while the card's own height was still correct. **A screenshot looked entirely plausible** (a panel below a panel); what settled it was dumping one pixel column and seeing the band's fill at x=8 where the card's fill should have been, and the panels' fill only from x=49. The interim patch (hand the band the same inset numbers) worked but was thrown away the same day when the user asked for the band's frame to be *separate* from the card — the band moved back onto the paper, and the need vanished with it. The lesson stands on its own: **when a layout is "some children in the padded box, one outside it", any new background layer has to answer for that one child explicitly — and "looks fine in the screenshot" is not a reading.**

- **`x:Load` breaks animations.** A `Storyboard`'s `TargetName` is resolved against the namescope at the moment `Begin()` runs, and a deferred element isn't in the scope yet, so the animation throws outright. The player's pause-pulse probe (`ProbePulse`) exists to pin exactly this. Before adding `x:Load` to anything to save startup time, confirm no `Storyboard` points at it and no code reaches it by name.
- **Don't lazy-load an element that code reaches by name.** The few milliseconds saved buy a field of null references.
- **`FrameworkElement.Parent` is null until the page has loaded.** So a reparent gated on it (`if (element.Parent is Panel current …)`) silently does nothing whenever it runs during `OnNavigatedTo` — and a page that decides its shape from the item it just fetched does most of its reparenting exactly there. Ask the two candidate panels instead (`HeroTail.Children.Contains(…)`, see `DetailPage.EpisodeHost`). The version that asked `Parent` survived from the day that strip started moving house (2026-09-01) on a race — the full-item round trip is usually slower than `Loaded`, so the second notification landed on the side where `Parent` existed — and lost it on the one path where the shell is collapsed while the frame re-navigates: coming back from a film (`ShellPage.RefreshActive` fires before `ShowPlayer(false)`). The self-check gate is 播放回来那一页.
- **The playback title bar is client area**, so dragging the window and minimise / maximise / close all have to be implemented by the page itself. Don't treat it as an ordinary title bar — the `InputNonClientPointerSource` machinery only covers browse state. Withdrawing a region declaration (`ClearRegionRects`, or an empty array) turns the whole strip permanently into client area, so after watching one film the window can no longer be dragged; the self-check asks `WM_NCHITTEST` about this on purpose.
- **Two pointer facts that keep biting.** WinUI raises `PointerMoved` when the content under a *stationary* pointer changes — treat that as real movement and auto-hide never fires. And `PointerExited` fires when the pointer merely moves onto a child of the same control — treat that as "left the window" and the overlay blinks out the moment a hand reaches for it. To decide whether the pointer really left the window, **ask the system**; don't read the coordinates off the event.
- **A recycled `ItemsRepeater` container's `Loaded`/`Unloaded` are not to be trusted either.** The recycle pool raises `Unloaded` on an element that is still painted on screen and `Loaded` never comes back (measured 2026-09-05 on four grey cards, re-measured 2026-09-12 on the home page's grey covers: `Unloaded` fires with `XamlRoot` still set, 3 ms after `Loaded`, and no further `Loaded` ever arrives). Any one-shot work gated on a `_live` flag therefore runs at most once per container — for `PosterCard`/`EpisodeRow` that meant every card later bound to the container *never issued its image request*: title and glyph normal, cover grey forever, and not one log line, because nothing failed. The fix is two rules: start the work in `OnCardChanged` unconditionally (a `Card` assignment has exactly one meaning — this container is about to show this item), and let `OnUnloaded` ask `XamlRoot` instead of believing the event (`if (XamlRoot is not null) return;`). The same shape bites anywhere a container-scoped side effect is triggered from `Loaded` alone.

- **The framework `.pri` files do not merge themselves in — a publish without them produces an app that cannot start, and 「just publish twice」 is a myth.** `EmbyNian.pri` has to contain the framework's `themeresources`, or the exe dies at `App.xaml` with `Cannot locate resource from 'ms-appx:///Microsoft.UI.Xaml/Themes/themeresources.xaml'` (exit code `0xC000027B`). The chain, measured bottom-up on 2026-09-11: `EmbyNian.pri` ← `makepri.exe new` ← `priconfig.xml`, whose third `<index startIndexAt="…pri.resfiles">` is the merge entry; `pri.resfiles` ← `@(_PriFilesFromPayload)`, and **that variant reads `@(PriOutputs)`** (`Microsoft.Windows.SDK.BuildTools.MSIX.Pri.targets:243`), **not `@(PackagingOutputs)`** — injecting into the latter does nothing at all, which is the first wrong turn. `PriOutputs` is filled by `GetPriOutputs` and holds only the project's own xbf/content plus `ProjectReference`; the framework PRIs ride the NuGet `runtimes-framework` asset channel and **never enter it**, so `pri.resfiles` is 0 bytes and `EmbyNian.pri` comes out 103–135 KB instead of 2.2 MB. The three live under each package's `runtimes-framework\win-x64\native\`: **WinUI** → `Microsoft.UI.Xaml.Controls.pri` (2 088 000 B, the one with `themeresources`); **InteractiveExperiences** → `Microsoft.UI.pri` (101 528 B — *not* in the WinUI package, the second wrong turn); **Foundation** → `Microsoft.WindowsAppRuntime.pri` (11 296 B). Fix: `AddWindowsAppSdkFrameworkPriToPayload` in the Shell csproj adds them to `PriOutputs`, and it must hang off **both** `BeforeTargets="_GetPriFilesFromPayload;_GenerateProjectPriConfigurationFiles"` — the latter depends on the former, so a later hook has already lost. **It is not a timing problem and re-running the publish is useless**: four consecutive publishes against a freshly cleaned `bin` all came out 135 KB. The old note in `CLAUDE.md` and the comment in `tools/verify-publish.ps1` both said otherwise and were disproved that day. A `Warning` inside the target fires if the three aren't found, meaning the package versions moved.

- **Diagnostic tool behavior depends on the current host and permissions.** Check exit codes and actual output files; a quiet command is not evidence it worked. If output capture is unavailable, use an explicitly permitted log file. Do not route a denied command through a `.cmd`, another shell or another agent to bypass the denial.

## Verifying a UI change

Reusable layout calculations already have Core tests such as `CardSizeTests`, `CardStripTests`, `WrapLayoutTests`, `HomeCarouselTests`, `ThemeTests` and `ScreenTests`. Extend the relevant tests when those calculations change, and still inspect the affected rendered layout: correct arithmetic does not prove correct binding or composition.
