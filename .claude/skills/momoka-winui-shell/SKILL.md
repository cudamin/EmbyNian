# Momoka — WinUI 3 shell terrain

Momoka is a WinUI 3 + Windows App SDK + .NET desktop client, unpackaged and x64. Read SDK and package versions from the project files, not this skill. Use the current working tree; an absolute path from another session is not its root.

**Policy lives in [CLAUDE.md](../../../CLAUDE.md).** This file explains the implementation and its constraints; general WinUI practice comes from the `winui-*` skills where it does not conflict with project policy. `PROGRESS.md` is the current-work and historical-evidence record. Before adding a service, inspect `src/Momoka.Shell/Composition/ShellServices.cs`, the registration site.

Use [momoka-playback](../momoka-playback/SKILL.md) for playback, [momoka-verification](../momoka-verification/SKILL.md) for interpreting verification evidence, and [mpv-shader-quality](../mpv-shader-quality/SKILL.md) for shaders and 画质档位. Current commands live in [docs/开发与验证.md](../../../docs/开发与验证.md).

## Three projects

- **`src/Momoka.Core`** — no UI references; currently no packages or project references. Package-free is a lightweight default, not a prerequisite for unit testing.
- **`src/Momoka.Shell`** — the WinUI shell. WindowsAppSDK is split into sub-packages rather than the meta-package to control payload size. The project file is authoritative for package selection and versions; review new runtime payloads during upgrades. `WindowsPackageType=None`, x64, `DISABLE_XAML_GENERATED_MAIN` with a hand-written `Program.cs`.
- **`tests/Momoka.Tests`** — currently package-free and referencing Core, with `OutputType=Exe` and a hand-written harness. `dotnet run` is the runner. Register new suites in `Program.cs`; compilation and run order are in CLAUDE.md.

## The shell's terrain

UI views are in `src/Momoka.Shell/Views/`, view models in `ViewModels/`, and registrations in `Composition/ShellServices.cs`. Entry points include the shell, home/library/detail/settings pages, server dashboard and player, with reusable controls such as `PosterCard`, `HomeBanner` and `EpisodeRow`. Enumerate the current files when a change spans the UI; an illustrative list here is not a completeness check.

`PlayerPage` is a sibling `UserControl` of the navigation shell rather than a page inside its `Frame`. It hosts the integrated composition pipeline; standalone playback uses mpv's own top-level window and uosc. See `momoka-playback`.

## Where capability lives

**`ShellServices.Build(AppPaths)` is the registration site.** It enables `ValidateOnBuild` and `ValidateScopes` and must run on the UI thread because `IUiDispatcher` captures that thread. Check the existing registration lifetimes before adding a dependency; the current use of singletons is not a reason to give every future object application lifetime.

Most non-UI capability sits in `Core/Emby`, `Core/Playback`, `Core/Mpv` and `Core/Configuration`; `Core/Services` contains selected services rather than all capability. Use dependencies and lifetime to decide whether a type needs registration. Moving a file into a folder named Services changes neither.

**Use the layering policy in CLAUDE.md.** Important business decisions, reusable calculations and regression-prone algorithms belong in testable Core code; local presentation predicates may remain near the UI. The current test-project reference is not a reason to extract every conditional. Existing reusable rules include:

`HomeLayout` (which home rows, in what order, and only writing settings back when something really changed), `ScreenPlacement` (which monitor, restoring geometry), `ItemArtwork.SamePictures`, `CardSize`, `ImageCachePolicy` and `LruCache` (eviction), `LoadGeneration` (which load is still the current one), `ItemMenu.For` (which menu rows and their wording), `CardStrip`, `WrapLayout`, `HomeCarousel`, `ItemMetadataEdit`, `EpisodeNavigation`, `TrackSelection` / `TrackLanguagePriority`, `StartupArgs`.

## Pages, view models, `Attach`

Pages created by this project's `Frame.Navigate` path use parameterless constructors. **Pages construct their own view models; dependencies arrive afterwards through `Attach(...)`.** Keep guards for calls made before those dependencies arrive, and inspect the file's `Attach`, cancellation and load methods before adding work.

**Service availability is only part of a session-bound page's lifetime check.** `DetailViewModel.Attached` requires `_active`, non-null settings and a current captured `_scope`; `HomeViewModel.Live` and `LibraryViewModel.LoadAsync` likewise check activity and session identity. Their `Cancel()` methods leave service fields populated, so a null check alone does not reject work after leaving the page or changing accounts. Preserve the existing entry guards and the operation's cancellation, request-generation and item/identity checks when applying asynchronous results. Simpler service guards in `SettingsViewModel` and `ServersViewModel` have different responsibilities; do not use them to replace the stronger checks in browsing workflows.

**`PlayerViewModel` is the only view model in the container**: a film keeps playing behind the library page, so its state has to outlive any navigation. `ShellPage.AttachWindow` resolves it and hands it to the page. `HomePage` marks its single resolution site with a comment saying it is the one place the page resolves anything — keep that habit, because a page reaching into the container from five places is how this rule rots.

Known deviation, not a template: `FilterPanelViewModel` is `new`ed with no `Attach` at all.

## Interfaces

**Don't invent an interface just because a class goes into DI** — with no second implementation and nothing to substitute or isolate, register the concrete class, which is what most registrations here do.

`ISecretProtector` separates platform protection from Core. `ISettingsService`, `IServerCapabilities`, `IUiDispatcher`, `IClipboard`, `ISystemLauncher` and `IShellActions` narrow access to capabilities: a page that needs settings should not acquire unrelated session or player operations. Keep that boundary even when only one production implementation exists; inspect current registrations and tests instead of maintaining counts here.

For a single operation, a method delegate may express the boundary more clearly than a new interface. Settings receives `PlaybackService.ApplySubtitleStyleAsync` without receiving play/stop/seek capabilities; the backend factory is also passed as a delegate. Use an interface when several related operations or a substitutable contract warrant it.

## Code-behind

The rule — pure UI behaviour may stay there, business capability may not — is in `CLAUDE.md`. **The test is "did business logic leak in", not "is there a binding".** Live examples: `ShellPage.xaml.cs` (the `_trail` / `_forward` breadcrumb stacks, library items built from what the server returned), `PlayerPage.Input.cs` (the three window buttons, which exist only on the player's title bar), `PosterCard.xaml.cs` (the hover layer). The counter-example: page-level busy/notice is *not* a code-behind toggle — it is a derived property on `PageViewModel` with `[NotifyPropertyChangedFor]`.

`Views/ItemCommands.cs` and `ItemCommands.Server.cs` are existing code-behind debt, not a template. They drive card commands through `EmbyClient`; some operations use `session.ExecuteAsync`, while downloads capture an `EmbySessionScope` so later work remains bound to the original identity. Inspect the relevant path rather than replacing every scope with the current session. Metadata field rules already live in `Core/Emby/ItemMetadataEdit.cs` with tests. Refactoring follows CLAUDE.md: extract a service when it improves responsibility, lifetime or testability, preserving confirmation and identity boundaries; being a large static class is not sufficient reason on its own.

## Colours: the role table, and why literal hex hides

Themes are declared in `src/Momoka.Core/Theming/UiThemes.cs`. Base colors expand into role colors through `UiTheme` / `ThemeColor`; `ThemeHost.cs` publishes the runtime brushes, while `Theme/Palette.xaml` supplies the first frame and `Theme/Styles.xaml` holds shared styles.

**Use role colors and the review procedure in CLAUDE.md.** The shipped themes are currently all dark, so screenshots alone may miss a hard-coded color. `AgreementsTests` checks literal-color growth, while palette self-checks check role completeness; neither proves the rendered result is correct. Keep the deliberately retained light half of `UiTheme` unless its documented rationale changes.

**The three dictionaries in `Palette.xaml` are keyed `Dark`, `Light` and `HighContrast`; there is no `Default`.** Add role keys to both `Dark` and `Light` and check the self-check's 「调色板浅色主题完整性」. Keep dictionary names aligned with `ThemeHost.Painted`, `ShellSelfCheck.Theme`'s `PaintedDictionaries` and `PaletteKeys` call, `ShellSelfCheck.Run`'s `PaletteKeys` call, and `App.xaml`'s `RequestedTheme`.

Distinguish lookup failures when diagnosing a theme that does not update. `ThemeHost.Apply` skips a dictionary it cannot find, so a typo in `Painted` can leave the active palette at its initial colors. A missing override of a framework resource may expose the framework value; a custom `Eg*` role has no guaranteed framework counterpart. Check the dictionary selected, the role key and the runtime update path instead of assuming every typo falls back to a framework color.

## XAML traps already paid for

The platform-wide ones — `x:Bind` defaulting to `OneTime`, `TextBox` needing `UpdateSourceTrigger=PropertyChanged`, `Converter={x:Null}` blowing up at runtime, attached properties needing static setters from C# — belong to `winui-design` and `winui-code-review` now and are deliberately not copied here, and since 2026-09-05 `Microsoft.WindowsAppSDK.Analyzers` reports them in gate 1 (wired in by `Directory.Build.props`; **`WUI2010` is the one WinAppSDK-analyzer rule this project turns off, reasoning in the Shell csproj** — separately, `Directory.Build.props` silences the platform-compat rule `CA1416` repo-wide). The ones below are this codebase's own.

- **For a mirror intended to stay centered, set and verify `RenderTransformOrigin`.** `ScaleX="-1"` otherwise flips about the top-left by default and can move the picture outside its visible band. The removed `HomeBanner` mirror wings exposed this in September 2026: geometry and stretch assertions passed while the picture was off-screen, and one pixel could not distinguish the scrim from real image content. Current `HomeBanner.Probe` does not assert `RenderTransformOrigin`; the existing XAML origin values and other layout checks are separate facts. When changing a transform, inspect the current assertions and verify both the intended origin and the rendered result; an old probe's coverage is not evidence for today's implementation.

- **An `Image` does not fill its cell — when a picture has to cover a box, it goes in an `ImageBrush`.** Under `Stretch="Uniform"`/`UniformToFill` WinUI's `Image` sizes itself to the *content* (09-10's banner batch measured "the element is the picture"), and its `ActualWidth`/`ActualHeight` then report the drawn picture rather than the layout box — so a reading taken off them can call a picture that overflows the band "filling it". `HomeBanner` hit both halves on 2026-09-11 while making the photo cover the band edge to edge: with `Stretch="UniformToFill"` the elements measured 1014×570 inside a 1014×341 band, and the screen showed the picture anchored at the band's **top** — the bottom 40% (the flower field) cut off, i.e. not the centred crop `UniformToFill` promises. Writing `Width`/`Height` = the band's inner box changed nothing. Caught by the self-check's own `PictureRead`, not by `Probe` (which had asserted the stretch mode, the alignment and the source and was green). Fix: two **empty** `Grid`s whose `Background` is an `ImageBrush Stretch="UniformToFill"` (its `AlignmentX`/`AlignmentY` default to `Center`, and a `Panel` with a background really does stretch to its cell) — the copy lives in the brush (`((ImageBrush)layer.Background).ImageSource`), and the element's size is then a box worth asserting on.

- **Keep an `ItemsSource` collection instance stable, and choose the update operation for the change.** `ObservableCollection` notifies on item additions, removals and moves; item-property changes need their own notifications. Incremental updates avoid disturbing selection or rebuilding every card. Use `Clear()` plus refill for a genuine whole-list refresh, not every small change. Replacing the collection without the required property notification can leave the binding on the old instance.

- **A hand-written card does not inherit the settings page's row-level switches, and 「隐藏功能下方说明」is the one that already bit.** `SettingRow.NotesHidden` is page-level state (`SettingsViewModel` aligns it on load and on the toggle) and the row templates bind `SettingRow.NoteVisibility` — a card written by hand inside a hosted page sits outside that template, so nothing collapses its note for it. 设置 → 通知's 「通知接管」card was exactly that: the switch was on, the paragraph stayed, and there was no error and no signal anywhere (user-reported 2026-09-30, one day after the card was written). Any future page-level flag that a row template happens to consume has the same shape. Fix pattern: keep the rule in one place (`SettingRow.NotesVisibility`, added that day) rather than copying it into the card's view model; have the view model expose it and re-raise it in `Attach` — navigation re-runs, which is the fresh-reading moment, the same reasoning as "the row's visibility is evaluated when its container lands on the tree"; and give the self-check a reading that compares the real `TextBlock.Visibility` against the flag (there is one, 「通知接管的说明跟着那一开关走」). Scope of that switch: 「各条功能下面的说明」only — card titles, the control, and the page's own intro line stay visible.
- **A visibility predicate that gains a conjunct on `IsCompact`/`HeroCard` must join `PageWidth`'s notify list — that is one half of its life; `AnnounceShape` is the other.** The 09-12 column/tail split gave `PickersVisibility` a `!HeroCard` half and the list only got `ColumnPickersVisibility`: on the episode page opened wide, the tail pickers evaluated Collapsed and nobody re-asked after the window crossed 1024 — 媒体源/音频/字幕 gone in the narrow window, not one error anywhere (fixed same day; the same batch's `VideoLineVisibility` and `HeroContentAlignment` carried it too). The attribute list on `DetailViewModel.PageWidth` is the tripwire: every property whose getter reads `IsCompact`, `HeroCard` or `IsEpisodePage` needs an entry there *and* a raise in `AnnounceShape`, because each of the two inputs can flip while the other's notification says nothing.

- **A sibling does not inherit another child's inner padding.** When adding a shared background, inspect which children are inside the padded container and which are siblings outside it; check their actual bounds against the background and corners. An earlier `DetailPage.HeroTail` layout mixed a padded `Viewbox` with an episode band outside it, letting the band cover a newly added card's margins. That layout has been retired: current `EpisodePanel` belongs to `BodySheet`, and `HeroTail` no longer contains that `Viewbox`. Keep the padding lesson, but use the current XAML tree when planning a layout change.

- **`x:Load` breaks animations.** A `Storyboard`'s `TargetName` is resolved against the namescope at the moment `Begin()` runs, and a deferred element isn't in the scope yet, so the animation throws outright. The player's pause-pulse probe (`ProbePulse`) exists to pin exactly this. Before adding `x:Load` to anything to save startup time, confirm no `Storyboard` points at it and no code reaches it by name.
- **Don't lazy-load an element that code reaches by name.** The few milliseconds saved buy a field of null references.
- **Check current container ownership before diagnosing a reparenting race.** `DetailPage.xaml` places `EpisodePanel` first in `BodySheet`; `DetailPage.PlaceEpisodes` only inserts it when that collection does not already contain it. The old hero/body switching path has been removed. Its historical failure was checking `Parent` before `Loaded`, when the property could be unset; if future code really needs early reparenting, inspect the candidate panels' `Children` and handle removal and insertion explicitly. Current `ShellPage.RefreshActive` reloads data on the existing page instead of navigating again. The 「播放回来那一页」 self-check checks the episode container and return scroll position through a simulated UI return without starting playback; it does not establish coverage of a live playback lifecycle.
- **The playback title bar is client area**, so dragging the window and minimise / maximise / close all have to be implemented by the page itself. Don't treat it as an ordinary title bar — the `InputNonClientPointerSource` machinery only covers browse state. Withdrawing a region declaration (`ClearRegionRects`, or an empty array) turns the whole strip permanently into client area, so after watching one film the window can no longer be dragged; the self-check asks `WM_NCHITTEST` about this on purpose.
- **Two pointer facts that keep biting.** WinUI raises `PointerMoved` when the content under a *stationary* pointer changes — treat that as real movement and auto-hide never fires. And `PointerExited` fires when the pointer merely moves onto a child of the same control — treat that as "left the window" and the overlay blinks out the moment a hand reaches for it. To decide whether the pointer really left the window, **ask the system**; don't read the coordinates off the event.
- **A recycled `ItemsRepeater` container's `Loaded`/`Unloaded` are not to be trusted either.** The recycle pool raises `Unloaded` on an element that is still painted on screen and `Loaded` never comes back (measured 2026-09-05 on four grey cards, re-measured 2026-09-12 on the home page's grey covers: `Unloaded` fires with `XamlRoot` still set, 3 ms after `Loaded`, and no further `Loaded` ever arrives). Any one-shot work gated on a `_live` flag therefore runs at most once per container — for `PosterCard`/`EpisodeRow` that meant every card later bound to the container *never issued its image request*: title and glyph normal, cover grey forever, and not one log line, because nothing failed. The fix is two rules: start the work in `OnCardChanged` unconditionally (a `Card` assignment has exactly one meaning — this container is about to show this item), and let `OnUnloaded` ask `XamlRoot` instead of believing the event (`if (XamlRoot is not null) return;`). The same shape bites anywhere a container-scoped side effect is triggered from `Loaded` alone.

- **The framework `.pri` files do not merge themselves in — a publish without them produces an app that cannot start, and 「just publish twice」 is a myth.** `Momoka.pri` has to contain the framework's `themeresources`, or the exe dies at `App.xaml` with `Cannot locate resource from 'ms-appx:///Microsoft.UI.Xaml/Themes/themeresources.xaml'` (exit code `0xC000027B`). The chain, measured bottom-up on 2026-09-11: `Momoka.pri` ← `makepri.exe new` ← `priconfig.xml`, whose third `<index startIndexAt="…pri.resfiles">` is the merge entry; `pri.resfiles` ← `@(_PriFilesFromPayload)`, and **that variant reads `@(PriOutputs)`** (`Microsoft.Windows.SDK.BuildTools.MSIX.Pri.targets:243`), **not `@(PackagingOutputs)`** — injecting into the latter does nothing at all, which is the first wrong turn. `PriOutputs` is filled by `GetPriOutputs` and holds only the project's own xbf/content plus `ProjectReference`; the framework PRIs ride the NuGet `runtimes-framework` asset channel and **never enter it**, so `pri.resfiles` is 0 bytes and `Momoka.pri` comes out 103–135 KB instead of 2.2 MB. The three live under each package's `runtimes-framework\win-x64\native\`: **WinUI** → `Microsoft.UI.Xaml.Controls.pri` (2 088 000 B, the one with `themeresources`); **InteractiveExperiences** → `Microsoft.UI.pri` (101 528 B — *not* in the WinUI package, the second wrong turn); **Foundation** → `Microsoft.WindowsAppRuntime.pri` (11 296 B). Fix: `AddWindowsAppSdkFrameworkPriToPayload` in the Shell csproj adds them to `PriOutputs`, and it must hang off **both** `BeforeTargets="_GetPriFilesFromPayload;_GenerateProjectPriConfigurationFiles"` — the latter depends on the former, so a later hook has already lost. **It is not a timing problem and re-running the publish is useless**: four consecutive publishes against a freshly cleaned `bin` all came out 135 KB. The old note in `CLAUDE.md` and the comment in `tools/verify-publish.ps1` both said otherwise and were disproved that day. The target removes missing input paths and warns only when **all three** framework PRIs are absent. One or two missing files do not trigger that warning; verify each resolved package path and the PRI merge inputs after a package change. `tools/verify-publish.ps1` checks the final `Momoka.pri` for `themeresources`, which detects that startup failure but does not prove that all three framework indexes were merged. Diagnose missing inputs from the current package layout and restore state rather than treating the warning as proof of a version change.

- **Diagnostic tool behavior depends on the current host and permissions.** Check exit codes and actual output files; a quiet command is not evidence it worked. If output capture is unavailable, use an explicitly permitted log file. Do not route a denied command through a `.cmd`, another shell or another agent to bypass the denial.

## Verifying a UI change

Reusable layout calculations already have Core tests such as `CardSizeTests`, `CardStripTests`, `WrapLayoutTests`, `HomeCarouselTests`, `ThemeTests` and `ScreenTests`. Extend the relevant tests when those calculations change, and still inspect the affected rendered layout: correct arithmetic does not prove correct binding or composition. Local presentation predicates follow the scope rule in CLAUDE.md. Gate timing and theme coverage come from CLAUDE.md; `momoka-verification` explains the evidence.
